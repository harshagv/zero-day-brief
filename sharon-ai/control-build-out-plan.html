Security control build-out plan — Security Engineer

Not a cover letter. A commissioning sequence for the control layer this role would own across two very different estates — a cloud control plane and a colocated GPU fleet — scored against evidence that would survive a second round of questioning rather than a first read.

Harsha G V harsha.gv29@gmail.com +61 402 697 098 au.linkedin.com/in/harshagv
Basis of this document

What it is built from, and what it assumes

Public information only

Nothing in this plan draws on non-public knowledge of Sharon AI's systems, vendors, network design, or security programme. It is built from the job description and public company sourcing. Four assumptions carry real weight, and are stated rather than resolved in the candidate's favour:

  • The on-premises estate is a colocated bare-metal GPU fleet, not corporate office IT. Public sourcing describes GPU capacity deployed inside third-party Tier IV facilities. This plan therefore treats "on-premises" as racks, fabric, out-of-band management and tenant isolation — the harder reading, and the one that produces the largest disclosed gap below.
  • The cloud estate is AWS and/or Azure. The JD offers AWS, Azure or GCP. Verified depth exists in the first two and none in the third; no GCP claim is made anywhere in this document.
  • This is a founding or near-founding security engineering hire. Nine distinct control domains sit under one headcount in the JD, which reads as build-the-function scope rather than a backfill into an established team. The sequencing below assumes that.
  • Compliance here means ISO 27001, SOC 2 and Australian sovereign obligations — not financial-services regulation. Framework references have been narrowed accordingly.

One item remains genuinely open: Australian Government Baseline clearance eligibility, which the JD raises under future IRAP work. It is citizenship-dependent and is a question for the first conversation, not something this document should imply either way.

Role decode

What the job does, versus what it requires on arrival

Responsibilities — the actual work
  1. Build and run the control layer across cloud and on-premises: firewalls, endpoint protection, SIEM, IAM, network security tooling.
  2. Lead vulnerability management end to end — scanning, triage, prioritisation, remediation tracking, across infrastructure and applications.
  3. Own incident detection, response and post-incident review.
  4. Run identity initiatives — privileged access management, SSO, MFA, Zero Trust.
  5. Embed security into the SDLC — secure code review, threat modelling, CI/CD pipeline security, Kubernetes and container hardening.
  6. Coordinate penetration testing and red team engagements and drive findings to closure.
  7. Partner with GRC on ISO 27001 and SOC 2 — implement technical controls, produce audit evidence.
  8. Evaluate and optimise security technology as capacity scales.
  9. Raise posture continuously through automation and monitoring.
Required & preferred — the arrival bar
  1. 5+ years in security engineering, security operations or infrastructure security.
  2. Hands-on cloud platform security — AWS, Azure or GCP.
  3. Networking and network security — firewalls, VPNs, DNS, TLS, Zero Trust.
  4. SIEM platforms, EDR/XDR, vulnerability management tooling, security orchestration.
  5. DevSecOps across CI/CD, Docker/Kubernetes, Terraform.
  6. Python, Bash or equivalent automation.
  7. Analytical and incident response capability; communication across technical and non-technical audiences.
  8. Preferred: CISSP, AWS Security Specialty, GIAC, OSCP or CEH.
  9. Preferred: AI infrastructure, GPU clusters, HPC or large-scale data centre environments.
  10. Preferred: ISO 27001 / SOC 2 environments; security automation at scale; Baseline clearance eligibility.

Role thesis. If hired, the job is to build the technical security control layer across two estates at once — a cloud control plane and a colocated bare-metal GPU fleet — and to convert that control layer into ISO 27001 and SOC 2 audit evidence fast enough that compliance never becomes the constraint on selling sovereign compute to government, research and enterprise customers.

Derived from three JD signals specifically: controls named across cloud and on-premises; compliance appearing twice (technical alignment, then GRC partnership with two named standards); and a clearance note that only exists where government workloads are in the pipeline.
Day one

The first real thing, before any new control is designed

The first deliverable is a single access-path inventory spanning both estates: every route into a customer's compute capacity — tenant API, operator administrative access, vendor and colocation access, out-of-band and baseboard management planes, the storage and network fabric — with the control gating each hop and the person who owns it named beside it.

The reason is structural rather than stylistic. This JD assigns nine control domains to one headcount. Without that inventory they arrive as nine parallel workstreams competing for the same engineering attention; with it, they collapse into one list ranked by consequence. The same artifact does double duty as the asset-and-access-control spine that an ISO 27001 or SOC 2 auditor asks for first, which means the compliance workstream starts producing evidence from week one rather than from a separate effort later.

It is also the honest onboarding move for this particular candidate: roughly half of that map — the bare-metal side — sits outside every environment worked in to date. Tracing it first is what makes the rest of this plan credible.

Build-out sequence

Commissioned by consequence, not by calendar

Ordering follows the same logic as the register above: the domains with the thinnest evidence get the earliest and most deliberate exposure, not the latest. Deferring them would make the first month look smoother and the third month considerably worse.

Band 1 — Highest consequence, thinnest evidence

Weeks 1–4
Why first: this is where the plan is most likely to be wrong, so it gets corrected earliest.
  • Build the access-path inventory described above across both estates, starting with the bare-metal side — tenant, operator, vendor and out-of-band management routes into compute capacity, each with its gating control and named owner.
  • Review multi-tenant isolation between paying compute customers: what actually separates one tenant from another at the node, network fabric and storage layers. Noted as an inference — the JD does not name tenant isolation, but a multi-tenant GPU cloud implies it as a first-order control, and this plan states the inference rather than presenting it as a requirement that was read.
  • Establish the ISO 27001 delta against controls already in place, using SOC 2 control engineering as the working method and treating the standards difference as a real one to be learned rather than assumed away.
  • Shadow the network and infrastructure teams on live firewall, VPN and DNS work as an observer. This is the second-thinnest domain in the register and gets deliberate early exposure for the same reason as the first.

Band 2 — Close a real gap, not a plan for one

Days 30–60
Why second: verified capability applied to whatever Band 1 actually surfaced.
  • Take the highest-consequence finding from the Band 1 inventory and close it end to end — scope, fix, test, deploy — rather than only documenting it.
  • Stand up vulnerability management as a running practice across infrastructure and applications with documented triage severity, prioritisation criteria and remediation tracking. This is the deepest verified domain in the profile and the fastest route to a visible result.
  • Baseline security-gate coverage across existing CI/CD pipelines — static analysis, dependency scanning, secrets detection, IaC validation, container scanning — using tooling already built and published for exactly this purpose, then extend gates wherever coverage is missing.
  • Pair on endpoint and SIEM platform administration specifically to convert detection-engineering experience into console-level ownership, which is the honest shape of that gap.

Band 3 — Take standing ownership

Days 60–90
Why last: ownership claimed only where the first sixty days have produced evidence for it.
  • Own identity end to end — privileged access paths into the fleet, SSO, MFA and Zero Trust enforcement — building on the PoLP design work that produced a measured incident reduction elsewhere.
  • Produce a detection coverage map against the access-path inventory: what is monitored, what is not, and what the alerting gaps mean in consequence terms. Joining an on-call rotation is part of this, not adjacent to it.
  • Scope the next penetration test with remediation tracking attached. Given no prior ownership of a testing engagement, the sensible arrangement is to run the first one alongside someone who has, and to say so rather than discover it mid-engagement.
  • Convert the closed findings and the control inventory into engineering-facing standards and secure defaults, using the reference-architecture and Security Champions patterns that worked at previous employers.

Questions

Three, each traceable to a specific line

1

Where does the boundary sit between Sharon AI's security responsibility and that of the colocation and hardware partners — specifically, who owns the out-of-band and baseboard management plane, and who owns the switching fabric? That answer decides whether "on-premises" in this role means operating network and security appliances directly, or engineering tenancy and access boundaries on top of infrastructure someone else runs. The two require very different ramp-up, and calibrating now beats assuming.

2

Is there an existing detection pipeline and on-call rotation this role would join, or is building the detection function itself part of the scope? Incident response experience here is a single, well-documented full-lifecycle Sev-1 rather than a high-volume practice, so knowing which of the two is being asked for changes what the first ninety days should honestly commit to.

— re: "Own security incident detection, response and post-incident reviews, partnering with internal teams to rapidly contain and remediate security events."
3

Is ISO 27001 currently pre-certification or in maintenance, and is IRAP assessment on the near-term roadmap? Producing audit evidence for an existing certification and building a control programme toward a first one are different pieces of work on different timelines — and the answer determines whether the compliance strand of this plan starts in Band 1 or Band 3.
