Not a checklist — the actual thinking, in the order I'd walk it

The method: find where data crosses from a lower-trust zone into a higher-trust one, ask what could go wrong at that specific crossing, then rank crossings by what happens to a real person if the control fails — not by how technically interesting the failure mode is.

1

Public → Edge: anonymous becomes authenticated

Both sides of this marketplace are vulnerable in different ways — participants because of disability or age, support workers because their livelihood depends on being matched. The question isn't just "can someone log in as someone else," it's "what does an attacker gain from a stolen participant session versus a stolen support-worker session," because the answer changes what the highest-value control is: session binding, an MFA prompt on new-device login, or rate-limiting credential-stuffing against a marketplace with two very different attacker incentives on either side.

2

Edge → Application: session becomes authorization scope

Does a support worker's session naturally exclude every participant's data except the ones they're actually matched with, enforced at the authorization layer — or is that boundary only enforced by what the interface happens to show? That distinction is the difference between a real access control and a UI convenience, and it's usually invisible until someone tests the API directly rather than clicking through the app.

3

Application → Third-Party: data leaves direct control

A care marketplace almost certainly outsources two things it shouldn't build in-house: payment processing and identity/police-check verification. Payment matters because PCI scope changes entirely depending on whether raw card data ever touches Mable's own services versus a hosted field or token vault. Identity verification matters because a police-check result is some of the most consequential data in the system — it's the control that decides whether a stranger is allowed into a vulnerable person's home. I'd want to know exactly what's retained on Mable's side after a check comes back: a pass/fail flag, or something more.

4

Application → Data: least-privilege service accounts

This is the boundary every service crosses to read or write real data, and it's usually the most over-permissioned one in practice, because it's built once early and rarely revisited. Does each service carry its own scoped database credential, or is there one shared "app" role touching every table? In a platform storing support-need and care-plan detail alongside standard profile data, a single over-broad service account is the difference between one compromised service exposing its own data and exposing everyone's.

5

Admin → Data: the boundary I'd prioritise first, not last

Every platform has an internal support or operations console. The honest question is whether it reads through the same audited, rate-limited service layer as the public app — or has a separate, more direct path to the data tier, built for convenience during a past incident and never revisited. In a platform holding health-adjacent support-need detail for a legally vulnerable population, that's the boundary where one over-trusted internal tool is worth more attention than another public-facing control most attackers will never reach.

What I don't know yet — and would verify on day one

  • Whether police-check/ID verification is built in-house or outsourced, and exactly what's retained after a check clears.
  • Whether the admin/ops console authenticates through the same identity provider as engineering staff, or a separate, less-monitored path.
  • Whether service-to-service data access uses per-service scoped credentials or a shared application role.
  • Whether payment data ever transits Mable's own infrastructure or is fully tokenised at the edge.

The real answer to all of this replaces every box above — this diagram is a starting hypothesis, not a finding. Building the real version of it is Tier 1 of the roadmap, not an afterthought.
