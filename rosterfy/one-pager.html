What this role would actually do — in plain terms

A non-technical summary of my Senior Platform Engineer — DevSecOps entry plan. No jargon, no acronyms without an explanation. Written for anyone deciding on this hire who isn't an engineer.

The one-sentence version

This job is about making sure the systems that run Rosterfy — where volunteer and staff data lives, how the app gets built and shipped, and how the new AI features work — stay safe by default, without slowing engineers down to get there.

Where I'm ready today, and where I'd be learning on the job

Color shows how confident I am, honestly, in each area — not how important it is. Everything here matters; this just shows where I'd add value from day one versus where I'd need time to catch up.

Building safety checks directly into the software delivery processReady now
This is what I already do in my current job — catching security problems automatically before software ships, instead of finding them after.
Controlling who and what can access sensitive systemsReady now
I've built this kind of access control before and measured a real drop in security incidents as a result.
Keeping compliance certificates (like SOC 2) backed by real, current proofReady, new tool
I've done this exact work before — just with different software than the specific tool (Vanta) Rosterfy uses today. The skill transfers; the tool is new to me.
Fixing security problems inside the website's own code, not just the servers it runs onRamping up
My experience so far has been at the infrastructure layer. I haven't worked directly inside this specific type of application code before, so this is a genuine gap I'd close early, not claim I already have.
Working on Rosterfy's second cloud provider (Google Cloud)New to me
All of my cloud experience so far has been on the other two major providers. I have no hands-on experience with this one yet and would say so plainly in an interview.
Being on call when something breaksRamping up
I don't yet have a track record of handling live incidents end to end. This is new ground for me and I'd want to shadow it early rather than be thrown into it.
Making sure the new AI assistant can't mix up one customer's data with another'sNew to me
I've used AI tools to help with security work before — that's a different skill from making an AI feature itself safe to use. I want to be clear about that difference rather than blur it.

What I'd actually do, in order

First month
Find out what's actually there. Right now, a lot of the cloud setup exists only because someone clicked buttons to create it — nothing is written down in a way that's easy to check or rebuild. I'd write all of it down first, before changing anything.
Second month
Fix one real thing, start to finish. Not a proposal — an actual fix, done properly, that other engineers can copy the pattern from.
Third month
Take ownership of one area for good, write down how it all works so the knowledge doesn't live only in my head, and be honest about which of the gaps above still need work.

The gaps, stated plainly

Three things I don't have yet, and won't pretend to:
  • Hands-on experience with Google Cloud, which runs part of Rosterfy's systems.
  • Direct experience fixing security issues inside the specific programming language (PHP) Rosterfy's website is built in.
  • A track record of handling a live incident from start to finish.
