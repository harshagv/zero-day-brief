Detect, remediate, or prevent?

Campaign #1 argued that severity ranking is the wrong way to order security automation work. This is me showing the working: six real AWS finding classes, and the reasoning I apply to each one before writing a single line of remediation code. Pick one on the left. Argue with me.

Read this before anything else on this page

None of it is drawn from your accounts, your configuration, your findings, or any non-public source. I have not scanned, probed, or enumerated anything belonging to you, and I would not.

The only facts here that came from you came from the job advertisement and from your public security page — which states that customer data is hosted on AWS and that the company holds ISO 27001 and SOC 2 Type II. That is the entire input.

The model I'm reasoning from

Four rungs, and the cost of stopping on the wrong one

Most security programmes stop at rung two and call it coverage. The distance between rungs two and four is where all the engineer-hours go — and it is the distance the job advertisement is describing when it says identify and correct, rather than identify.

Rung 4 is not always the right answer. A control that needs a human judgement about workload intent belongs on rung 1 forever, and automating it is actively harmful. Choosing the rung is the skill. Building the automation is the easy part.
The walkthrough — click through these with me

Six findings, six different answers

Each of these is a control that fires in almost every AWS estate. Each one gets a different rung, for a different reason. Where I say something would break, that is the part I most want challenged.

Finding class

Rung 4 — Prevent

If it came back after you fixed it, the bucket was never the defect.

This is the single most misdiagnosed class of finding I've dealt with. Someone remediates the bucket, closes the ticket, and the same control fires again six weeks later on a bucket created from the same module. Everyone treats it as two incidents. It is one defect, in a template, counted twice.

What I check first
Whether any resource in this class has previously been marked resolved and is now active again. That single signal reclassifies the whole class — it's the strongest evidence available that the fix is being applied downstream of where the mistake is made.
What I'd build
A Terraform module default plus an IaC policy check that fails the plan, not the deploy. Auto-remediation here would work and would still be the wrong answer, because it would quietly repair the symptom every month and hide the fact that the module is wrong.
Why not just auto-remediate as well
You can, and for the existing fleet you should — once. But if the auto-remediation stays on permanently, nobody ever feels the pain that would make them fix the module. I've seen automation used as a way to never fix root cause.
Where this judgement could be wrong

If your buckets are created by a dozen unrelated teams with no shared module, there is no single template to fix and this collapses back to rung 3. I'd need to see how buckets actually get created here before committing to it.

Rung 1 — Detect, deliberately

The highest-severity finding on the list is the one I would never automate.

A wildcard action in an IAM policy is critical. It is also, quite often, load-bearing. Scoping it down correctly requires knowing what the workload actually calls — which means reading CloudTrail for that principal, not reading the policy. There is no safe generic fix.

What auto-remediation would do
Break a production data pipeline at 2am, get the automation switched off by an incident commander, and cost you every other auto-remediation you'd built. One bad automation poisons the well for all of them — that's the real damage, not the outage.
What I'd build instead
Access-analyser-driven least-privilege proposals generated from actual CloudTrail usage, delivered to the owning team as a pull request they approve. Automation that proposes rather than acts. Same leverage, no blast radius.
The one thing I would automate here
Blocking new wildcard policies at the pipeline. Existing ones need a human; new ones don't need to exist.
Where this judgement could be wrong

If your IAM is already fully managed through Terraform with no console access, "existing" and "new" collapse into one category and this moves to rung 4 immediately.

Rung 3 — Remediate, with a rollback

Yes, close it automatically. No, not without a way to undo it.

An unrestricted ingress rule on a non-load-balancer security group is about as close to a mechanical fix as this domain gets. I'd automate it. But the thing that makes auto-remediation safe isn't the fix — it's what happens in the ninety seconds after you get it wrong.

What the automation must include
The prior rule state captured before revocation, a single command to restore it, and a message to the owning team's channel naming what was changed and how to reverse it. If the rollback isn't built, the remediation isn't finished.
The carve-out that always exists
Some group genuinely needs 0.0.0.0/0 on 443. There will be a tag-based exemption path, it will be abused within a quarter, and so the exemption needs an expiry date and an owner — otherwise you have built a permanent bypass and called it a control.
Why not rung 4
You should also block it in IaC. But security groups get edited in the console during incidents by people with legitimate break-glass access, so prevention alone leaves a real gap. This is one of the cases where you want both rungs, not the higher one.
Where this judgement could be wrong

If console access to production is already fully removed, the drift path I'm protecting against doesn't exist, and building the remediation is wasted effort.

Rung 1 — Detect, then go and ask

"Public bucket" is a finding. It is not automatically a problem.

This is the one that catches people out. A platform serving media to millions of users has buckets that are meant to be publicly readable, and a security engineer who auto-remediates public access without checking is going to take down image delivery and learn a memorable lesson about trust.

The question that actually resolves it
Not "is it public" but "is it public and does it contain anything other than deliberately-published assets". Those need different signals — object-level inspection, or better, a naming and account convention that makes the answer structural instead of investigative.
What I'd build
A hard split: public-content buckets live in a dedicated account with block-public-access disabled by design and nothing else in it. Every other account has block-public-access enforced at the account level and cannot be turned off. Then the finding becomes unambiguous — public in the wrong account is always an incident.
Why this is the interesting one
It is the case where the correct security engineering move is an architecture change that makes the question answerable, rather than a detection that makes the question askable more often.
Where this judgement could be wrong

Splitting accounts is expensive and disruptive. If the public-asset surface is small and stable, an allowlist is the proportionate answer and the account split is over-engineering.

Rung 1 — because rung 3 is not physically available

You cannot automate enrolling somebody's phone.

I'm including this one because a naive leverage score gets it wrong, and I want to show the failure rather than hide it. High severity, repeats constantly, mechanical-sounding — every heuristic says automate it. But there is no remediation action that a machine can take. The only automatable move is revoking the user's console access, which is a business decision wearing a technical costume.

The real fix isn't remediation at all
It's eliminating the object class. IAM users with console passwords shouldn't exist in an estate with a federated identity provider. The finding disappears when the users do — which is rung 4 reached by deletion rather than by policy.
What this tells you about scoring models
Any automation-backlog score needs a hard veto list, not just weights. My own tool has one, and this control is on it, with a regression test that fails if it ever gets classified as auto-remediable.
Where this judgement could be wrong

Break-glass IAM users are a legitimate pattern and should survive the cull. If most of your findings are break-glass accounts, the right answer is a documented exception register, not deletion.

Rung 4 — Prevent, at account creation

This finding is never about logging. It's about how accounts get made.

If CloudTrail is missing in one account, that's a gap. If it's missing in four, the account vending process is the defect and every control you care about is probably missing there too — this one just happens to be the one with a detection attached.

What I'd actually look at
Not the trail. The account baseline: whether new accounts are created from a controlled pipeline with a mandatory control set applied, or created by hand and remembered about later. The CloudTrail finding is a smoke detector for that, and it's the cheapest smoke detector you have.
What I'd build
Organisation-level enforcement — trail, config recorder, GuardDuty, and block-public-access applied from the management account so a member account cannot be created without them and cannot disable them locally.
Why this is first in my ranking, not tenth
Because account spread is the strongest available proxy for "this is a systemic gap, not N incidents", and systemic gaps compound while individual findings don't.
Where this judgement could be wrong

Sandbox and experimentation accounts may be deliberately outside the baseline. If so, the finding count is noise and the real work is excluding them cleanly rather than enforcing into them.

This reasoning already exists as code

The ranking above isn't a slide — it runs

I built the scoring model as a small tool before writing this page, so the ordering here isn't something I argued into existence. It's output. Zero dependencies, standard library only, thirteen tests including two regression guards for bugs I hit while building it. Run it against an exported findings file and it produces this:

$ python3 finding_automation_triage.py findings.json AUTOMATION BACKLOG - ranked by engineer attention consumed, not severity ============================================================================== # TIER FINDING CLASS LEVERAGE COUNT ACCTS ------------------------------------------------------------------------------ 1 PREVENT CloudTrail.2 64.0 4 4 -> present in 4 accounts - this is a baseline gap, not N incidents 2 PREVENT S3.4 30.0 3 2 -> recurred after remediation - the IaC template is the defect * 3 REMEDIATE EC2.2 8.0 2 2 -> deterministic fix, low volume - automate when convenient 4 DETECT IAM policy allows overly pe... 20.0 2 2 -> fix depends on workload intent - auto-remediation would break something 5 DETECT IAM.5 12.0 3 1 -> no deterministic fix pattern matched - keep a human in the loop ------------------------------------------------------------------------------ * = regressed after remediation Parsed 15 finding(s); skipped 1. skipped 1: no Compliance.SecurityControlId, GeneratorId or Title

Note row 4: a leverage score of 20 sitting below a score of 8. That's deliberate. Tier beats score, always — because a high-leverage finding that can't be safely automated still can't be safely automated. The skipped-record count is printed rather than swallowed, because a triage tool that silently drops input is worse than no tool.

What would kill each of these judgements

The questions I'd need answered before any of this survives

This is the part I'd actually want to spend the interview on. Every row is a judgement above that I would abandon on the spot given the right answer.

What I'd need to know
What changes if the answer surprises me
Are AWS accounts created from a vending pipeline with a mandatory baseline, or by hand?
If vended, the CloudTrail panel is solved already and my top-ranked item is wrong. The backlog reorders around whatever the baseline doesn't cover.
Is console access to production still available, or has it been removed?
If removed, the entire drift-remediation rung collapses. Everything moves to prevention and the security-group automation stops being worth building.
Are buckets, security groups and IAM created from shared modules, or per team?
Shared modules make prevention cheap and remediation nearly pointless. Per-team creation inverts that completely.
What does the public-asset surface actually look like for a platform serving millions of frontline users?
If it's large and dynamic, the dedicated-account split is right. If it's small and stable, I'm over-engineering and an allowlist wins.
Who currently gets paged for a Security Hub finding, and how often?
This is the number the whole leverage model is a proxy for. If you already measure it, my proxy is redundant and I'd use your real data instead.
