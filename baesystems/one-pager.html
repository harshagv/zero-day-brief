What this proposal is, in plain terms

A non-technical translation of the entry plan for the Product Security (Cyber) Engineer role on JORN — no jargon, no acronyms without an explanation.

Prepared by Harsha G V  ·  harsha.gv29@gmail.com  ·  +61 402 697 098

The one-sentence version

Make sure every security rule the program has to follow is actually being followed — with proof — not just written down somewhere and forgotten.

Why that's harder than it sounds

A defence program like this has security rules coming from a lot of places at once — customer contracts, government policy, industry standards. Each rule needs someone to (1) assign a specific fix or safeguard for it, (2) prove that fix actually works, and (3) keep that proof up to date as the design changes. When step 2 or 3 gets skipped, that's usually what an audit or a security incident finds first — a rule that looked handled on paper but wasn't, in practice.

The first useful thing to do in this role isn't to advise on any one design. It's to check whether that three-step chain — rule → fix → proof — actually holds together for what's already in place, and fix the links that don't.

The first 90 days, in plain terms

  • Days 1–30Learn how the program currently tracks its security rules, and check one real example against a small checking tool built specifically for this (already working, not just planned).
  • Days 31–60Fix the first real gap that check finds, start to finish — not just report it. Also sit in on how the team checks the security of parts and components bought from other companies, since that's the one area with no relevant experience yet.
  • Days 61–90Take ongoing responsibility for one area of this tracking, and have a straight answer — with a real plan attached — for the parts of the role that are still being learned.

Readiness, at a glance

Keeping track of changes and proving they were checked properlyStrong
Automating repetitive security checks so they actually get doneStrong
Explaining risk in plain language to non-technical peopleStrong
Reviewing whether a design meets its security requirementsPartial
Checking the security of parts or systems bought from other companiesNot yet
Australian defence-specific security rules and standardsNot yet
Physical security and the security of hardware itselfNot yet
Said plainly, not softened

This background is strongest in software and cloud security — proving rules are followed through automation and documentation. It's weakest in the parts of this role specific to physical hardware, supplier checks, and Australian defence standards. That gap is real and would take deliberate, fast learning in the first few months, not something already in place.
