Day one

The first real move

Tied to the position description's own framing of the deliverable.

The first artefact is not a pipeline template. It is a current-state coverage map of every pipeline already running at Bupa — which repositories build through which tooling, which have SAST, SCA, secrets scanning and container scanning wired in, which enforce a quality gate that can actually fail a build, and which reach production without an approval that leaves evidence behind.

The reason is structural. A golden path is only golden relative to what teams are doing now; a reference template written without that map is a guess about which constraints teams will refuse to accept, and the migration stalls at the first team whose build doesn't fit. The coverage map turns "standardise the toolchain" into a ranked migration order — worst-covered and highest-consequence services first — and it doubles as the baseline the programme is later measured against.

The candidate already maintains a tested, standard-library-only scanner built for exactly this question: it parses GitHub Actions, Azure Pipelines and GitLab CI definitions and reports which security gates are present, absent, or present-but-non-blocking. It is pointed at repositories on day one, not written from scratch in month two.

How adoption gets measured

Four rungs, so "scaled across technology" means something specific

The position description makes migration and adoption a named accountability but leaves the finish line undefined. This is the definition the plan below is built against — every team sits on exactly one rung, and the programme's health is the distribution, not the template's existence.

Rung 0

Unmanaged

Hand-rolled pipeline, no shared template. Security scanning absent, or present and non-blocking. Production access governed by convention. These teams are ranked first by consequence, not by willingness.

Rung 1

Template-consuming

Building through the reference template, but with gates in warn-only mode. This rung exists deliberately — forcing a team from Rung 0 straight to enforcement is how platform migrations acquire a reputation for breaking builds.

Rung 2

Gate-enforced

Quality gate and security gates fail the build at an agreed severity threshold. Branch protections and pull-request policy active. Deployment approvals leave evidence automatically.

Rung 3

Policy-governed

Template consumed by reference rather than copied, so platform changes propagate. Any deviation runs through the documented exception process with a named owner and an expiry date — which is what keeps the standard a standard instead of a starting point teams fork away from.

Delivery plan

Three waves, ordered by what a migration actually fails on

Sequenced against the adoption model above rather than the calendar. The failure mode this ordering guards against is a technically excellent template that no team migrates onto.

Wave 0 · Days 1–30

Measure before standardising

Baseline the estate
  • Run the pipeline-coverage scanner across accessible repositories to produce the current-state map: which pipelines have SAST, SCA, secrets and container gates, and which of those gates can actually fail a build.
  • Place every team on a rung and rank migration order by consequence — services handling member and claims data first, not the teams most willing to move.
  • Inventory the SonarQube estate specifically: version, quality profiles in use, gate configuration, permission model, upgrade path. This is the least-evidenced named accountability, so it gets the earliest deliberate exposure rather than the latest.
  • Get the real answer on build-runtime distribution across the estate, since the .NET share determines how much of the template work sits on the candidate's weakest ground.
Wave 1 · Days 31–60

One pipeline, all the way through

Ship the reference, don't document it
  • Build one complete golden reference pipeline with a single real delivery team as the pilot — all eight stages, running in production, not a template in a repository nobody consumes.
  • Move that team from Rung 1 to Rung 2: gates switched from warn to blocking at an agreed severity threshold, with the noise tuned out first — the same detect-before-prevent sequencing used when promoting custom endpoint detections at Mox Bank.
  • Close the two hardest personal gaps against real work rather than in the abstract: SBOM generation wired into the package stage, and the .NET build path built alongside an engineer who owns that stack.
  • Write the exception process before it is needed. A standard with no documented variation path gets bypassed quietly instead of challenged openly.
Wave 2 · Days 61–90

Make it adoptable by people who weren't in the room

Scale past the pilot
  • Onboard the next cohort of teams using documentation and a self-service onboarding guide rather than direct pairing — the point at which the standard either scales or reveals it only worked with its author present.
  • Publish the rung distribution as a running metric so "adoption across technology" is a number on a dashboard, not an assertion in a steering update.
  • Stand up the Security-Champions-style enablement pattern proven at OSL Group, adapted to Bupa's team structure, so pipeline questions route to a network rather than to one platform engineer.
  • Hold a documented, unflattering account of where ramping is still incomplete — SonarQube administration, .NET, progressive delivery — with dates against each, not a vague acknowledgement.

Questions

Is the SonarQube instance self-managed and currently owned by a named team, or has ownership drifted — and does "upgrades" in this role mean routine version maintenance or an overdue migration off an unsupported release?

A bullet this specific usually describes an instance nobody wants. The answer changes whether this is a maintenance responsibility or a project in its own right, and it changes the ramp plan in Wave 0.

What is the actual build-runtime distribution across the estate — what share of pipelines being standardised are .NET versus everything else?

Asked because it is the requirement with the weakest evidence behind it. If .NET is the overwhelming majority of the estate, that is worth establishing in the first conversation rather than the third.

Who holds authority to grant an exception to the standard — this role, application security, architecture, or the delivery team's own leadership?

The exception process determines whether the golden path is enforceable or advisory. If exceptions are granted outside the platform, adoption metrics measure goodwill rather than governance.
