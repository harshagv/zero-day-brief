Not a cover letter. This job description asks for security that runs itself. So this document audits the candidate against that axis directly: for every control domain the role names, has this work previously been delivered as a manual practice, a semi-automated one, or a self-enforcing control and is there evidence behind the answer, or isn't there.

01 — Day-one thesis

The first artifact this role needs

The job description asks this role to correct misconfigurations, not review them. That single verb sets the first deliverable: a per-finding-class ledger across every AWS account that answers one question for each class of misconfiguration — does a human currently have to touch this, and how often does it come back? Recurrence multiplied by manual touch is the automation backlog, ranked. Nothing else produces a defensible order of work, because a severity-only ranking optimises for the scariest finding rather than the one costing the most engineering attention every week.

That ledger is also the honest onboarding instrument. It requires reading the existing detection surface before proposing anything, and it produces a baseline the posture uplift can later be measured against — which the job description asks for explicitly, and which cannot be claimed retroactively without one.

03 — Prioritised plan

Ranked by automation leverage, not by calendar

Ordering rule: the work that removes the most recurring human touches per unit of engineering effort goes first. The two weakest rows in the ledger get deliberate early attention rather than being deferred to the end where they would be least visible.

Weeks 1–4
Leverage:
baseline first

Build the ledger before building anything else

  • Produce the per-finding-class inventory from the day-one thesis across all AWS accounts: for each class, whether detection exists, whether correction is automated, how often it recurs, and who currently touches it.
  • Baseline existing CI/CD security-gate coverage — SAST, SCA, secrets, IaC — per pipeline, using tooling already built for this purpose rather than starting from a blank page.
  • Re-establish current AWS working depth deliberately. The strongest AWS evidence in this document is from roles ending January 2025; the two most recent roles are Azure-stack. That recency gap is real and is addressed by doing the work in week one, not by asserting it away.
  • Resolve the two scoping ambiguities named in the basis note — what "system hardening" and "lead assessments" mean in practice here — with the hiring manager rather than guessing.
Weeks 5–8
Leverage:
highest recurrence

Convert the top recurring finding class from detect to correct

  • Take the single highest recurrence-times-manual-touch finding class from the week-four ledger and ship its auto-remediation end to end — detection, guardrail, correction, rollback path, and the metric that proves it stopped recurring.
  • Close the language question honestly: if the existing security automation codebase is Go, that becomes the ramp target in this window and is treated as a real learning cost, not a formality. If it is Python, this is immediately productive ground.
  • Push at least one correction upstream into an IaC guardrail so the misconfiguration cannot be reintroduced — the pattern that produced the Terraform-enforced CI guardrail after the OSL Group edge-cache incident.
Weeks 9–13
Leverage:
own a domain

Take standing ownership, and start on the gaps that can't be shortcut

  • Assume standing ownership of AWS posture automation and vulnerability management — the two domains with the deepest verified evidence — including their cross-squad prioritisation cadence.
  • Take the honeypot design from academic scale to production scale with whoever owns detection today — the isolation, egress-containment, and log-routing pattern already exists and works; what it has never had is a real adversary, a real blast radius, or an on-call rotation attached to its alerts. Prior work also includes a synthetic cross-identity canary built after a live incident, which is the same instinct applied to a production system.
  • Report the posture delta against the week-four baseline to engineering and to leadership — the two audiences the job description names — which is also the fastest way to convert the weakest row in this document into evidence.
  • Take on endpoint platform administration deliberately — console and policy ownership, not agent deployment — to close the one remaining distance between authoring detections and owning the platform they run on.
  • Apply the golden-image pattern to whatever the current base image story is: hardening enforced at build, agents baked in, drift impossible rather than detected. This is the strongest transferable mechanism in this background and the fastest route to a measurable posture number.

05 — Domain coverage

Where the depth is, and where it isn't

The recency problem, named before anyone else has to raise it

This job description is AWS-only. It does not mention Azure once. The AWS evidence in this document is real, quantified, and multi-account — and it comes from roles that ended in August 2023 and January 2025. The two most recent roles are Azure-stack: Azure DevOps, Azure Policy, Defender for Cloud, Key Vault. That is roughly nineteen months since AWS was the primary daily environment.

The underlying skills — multi-account posture, identity design, detection pipelines, pipeline guardrails — transfer directly and the mental model is intact. But an interviewer reading the résumé top-down will see Azure first and has every reason to test how current the AWS is. 06 — Questions

Each traceable to a specific line

1

What language is the existing security automation actually written in? The job description treats Golang, NodeJS, and Python as interchangeable, but a codebase is not — inheriting a Go automation estate is a materially different first quarter than extending a Python one, and it changes what the first shipped control should be.

— re: "strong coding experience in Golang, NodeJS, or Python"
2

Is there deception tooling in the estate today, and what is it expected to catch — opportunistic internet scanning, or lateral movement by something already inside? Those need different placement, different decoy content, and different alert thresholds. The honeypot work behind this document was built for the first case; production deception in an environment serving millions of users is usually built for the second.

— re: "Build automated security controls, monitoring, and reporting systems (vulnerability management, logging, integrity, honeypots, etc.)"
3

Does this role's hardening and detection scope stop at the production AWS estate, or does it extend to the corporate fleet — identity, laptops, SaaS? The two are listed in different sections of the job description, which usually means different owners. The production side is where the evidence in this document sits; the corporate identity stack is where it doesn't.

— re: "Experience securing corporate IT systems such as Okta, GSuite, Kandji & InTune" · "from vulnerability management and system hardening to security automation and architecture"
