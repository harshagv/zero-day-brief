01 — Day-one thesis

Where this starts

Before offering technical advice on any specific design, the first task is mapping where security requirements currently live — across specifications, supplier deliverables, and review records — into a single requirement-to-control-to-evidence trace feeding the safety case. That discipline is already practiced in adjacent regulated environments: SOC 2 Type II control traceability, CIS/NIST compliance mapping. Applying it here means learning this program's own structure and standards first, not assuming a cloud-security traceability model transfers wholesale onto a defence hardware/software program.

↳ re: "Maintain design integrity and associated documentation in line with relevant configuration management, change management, and traceability protocols"

03 — Entry plan

First 90 days

Days 1–30

Learn the trace as it exists

  • Get access to existing product security requirement sets, supplier security clauses, and safety case documentation structure; build a single requirement→control→evidence trace for one in-flight work package — learning PSPF/DSPF/ISM/RMF terminology on this program's own terms rather than assuming CIS/NIST fluency carries across.
  • Shadow a supplier security review cycle as an observer. This is the cleanest gap on record, so it gets the earliest and most deliberate exposure, not the latest.
  • Sit in on a peer review cycle of existing product security documentation to learn the program's configuration-management conventions before contributing independently.
Days 31–60

Contribute one real trace

  • Take ownership of the requirement→control→evidence trace for one component end to end, applying the same "build the tool, not the description of it" discipline evidenced in the IaC automation work at Mox Bank.
  • Participate directly in one supplier security engagement, specifically to close the procurement gap flagged in Section 02 rather than leave it a standing assumption.
  • Contribute to one documentation peer review cycle as a reviewer, not just an observer.
Days 61–90

Own a trace domain

  • Take standing responsibility for configuration/change-management traceability on one product area, including its program status reporting.
  • Have a documented, honest position on PSPF/DSPF/ISM/RMF fluency and supplier-review depth, with a concrete study or certification plan attached (e.g. a defined path toward CISSP) — not a vague acknowledgment of the gap.
