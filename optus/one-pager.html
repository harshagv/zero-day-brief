Plain-language briefing

Keeping the security systems themselves reliable

A non-technical translation of the entry plan for the Senior Security Platform Engineer – SRE role, for anyone reading it without a security or engineering background.

For: a non-technical stakeholder deciding whether this plan makes sense · Companion to entry-plan.html

This role isn't about catching hackers directly. It's about making sure the systems that catch hackers actually keep working — and keep working fast enough to matter.

The plain-English version

Optus runs several specialist security systems: one that watches for suspicious activity across the whole company (like a security camera network), one that protects individual laptops and servers (like a lock on every door), and one that scans for known weaknesses before someone else finds them first.

Those systems only help if they're actually running properly, all the time. A camera that's technically switched on but hasn't recorded anything in six hours is worse than no camera, because everyone assumes it's working. This role exists to make sure that never happens quietly — that if a security system starts to fail, the team knows within minutes, not after something's already gone wrong.

Think of it like a hospital's alarm systems team, not the doctors. The doctors respond to patients. This role makes sure every alarm, monitor, and alert in the building is actually working, calibrated correctly, and reaches the right person fast enough — so the doctors' response time isn't quietly degraded by a system nobody was watching.

Jargon, translated

TermIn plain English
SLOA promise about how reliable a system should be — "this security camera should be recording 99.5% of the time," made specific enough to measure.
Error budgetThe small amount of allowed failure built into that promise — not zero, because chasing perfection everywhere is wasteful, but a clear, agreed limit.
Burn rateHow fast that allowed failure is being used up right now — a slow, steady leak versus a sudden burst, which need different responses.
SIEMThe system that collects and cross-references security signals from across the whole company, looking for patterns a single alert would miss.
EDRSoftware running on individual laptops and servers that watches for and can stop malicious activity directly on the device.
Observability-as-codeBuilding the monitoring and alerting itself the same disciplined way software is built — tested, version-controlled, repeatable — instead of clicking through settings by hand.

What's honestly still missing

Eleven years of security engineering experience doesn't automatically transfer into this specific discipline. The parts about building automation and cutting manual work are strong and provable. The parts about formally defining reliability targets, leading a major incident, and forecasting capacity are not — those would be genuinely new skills being built on the job, not skills quietly assumed to already be there.

Three questions worth asking before day one

Do these reliability promises already exist for the security systems, or would someone be creating the first ones from scratch?

When one of these systems has a major failure, who's in charge of coordinating the response — this role, or a separate team?

Is there already a way to see how close these systems are to running out of room to grow, or would that need to be built too?
